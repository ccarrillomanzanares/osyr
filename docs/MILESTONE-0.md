## Disk installer (30 Oct)

`osyr-install` (Python, in the overlay). It runs from the USB and **wipes the whole disk**. Interactive: lists the disks (never the USB's, nor read-only ones or those under 24 GB), summary of what is there and what gets wiped, confirmation by typing the disk name, and the /home passphrase twice (min. 8). Without questions: `--disk /dev/sdX --confirm sdX --passphrase-file F`; `--list [--json]`. On an already installed OSYR (`/etc/osyr/install.conf`) it refuses.

| Partition | Contents |
|---|---|
| sector 0 and gap up to 1 MiB | `boot.img` (440 bytes) and GRUB BIOS core, like the USB |
| 1, ESP FAT32 256 MiB | `EFI/BOOT/BOOTX64.EFI`, `osyr/grub/grub.cfg`, `osyr/grub/grubenv` (`slot=a`) |
| 2, root A ext4 | copy of the running system (bind of `/`, `cp -a`), without `/home` |
| 3, root B ext4 | empty, for A/B (milestone 4) |
| 4, LUKS2 → ext4 | `/home` copied from the USB; `crypttab` with `tries=0` (root is locked: emergency mode would be of no use) |

Roots of 1/8 of the disk, between 8 and 16 GiB. Everything is copied as is: password, language, wifi, providers and history stay the same.

Decisions:
- **MBR and not GPT** (a change from the handover design): it is the USB's scheme, which already boots in BIOS and UEFI on both laptops, and GRUB BIOS goes in the gap without patching sectors. Exactly four primaries; if more are needed (or disks > 2 TiB), move to GPT with a BIOS boot partition.
- The kernel does not go in the ESP: GRUB reads it from `/boot/bzImage` on the active root (`search --fs-uuid`), so an A/B update changes system and kernel at the same time. `root=PARTUUID=<signature>-02/03`.
- The disk has its own GRUB cores (`post-build.sh` → `/usr/lib/osyr/boot`, with `loadenv`), which look for `/osyr/grub/grub.cfg`: with the USB and the disk both plugged in, each one boots its own (the USB's looks for `/boot/grub/grub.cfg`).
- New packages: `cryptsetup` (systemd builds `systemd-cryptsetup` with it; forces a build from scratch) and `dosfstools` (`mkfs.vfat`). The kernel already had `DM_CRYPT` and XTS `=y`.
- The agent does not run it: it points to `sudo osyr-install` in a terminal.
- UEFI without an NVRAM entry (there is no `efibootmgr`): the fallback path `EFI/BOOT/BOOTX64.EFI` is used, which almost every firmware boots. The HP 15-ba is BIOS.

Tested before building, on the VPS: installation onto a loop disk with the root of the `dbd89d6` image (without LUKS at boot, that image has no `systemd-cryptsetup`) and boot in QEMU in BIOS, in UEFI and with `slot=b`. Built from scratch with cryptsetup (30 Oct) and `make test` **103/103** (native 9, vm 83, install 11), not committed yet. Found by the test: the image does not ship `wipefs` (a util-linux option not enabled); it is not needed, `sfdisk --wipe always --wipe-partitions always` erases the old signatures (checked by reinstalling over an installation with LUKS). Full test in `make test-install` (the `install` phase of `make test`): installs from the USB in QEMU to a second disk, boots it in BIOS (wrong and right passphrase over the serial console) and in UEFI with the USB also connected.

## Code updates without rebooting (1 Nov) — v0.29.1 (code)

## Image update: A/B slots (1 Nov) — v0.27.0

- **`osyr update image check|apply|rollback|status|confirm|fallback`** (`osyr/image.py`, `osyr/slots.py`): downloads `osyr.img.xz` (curl with `-C -` to `/home/.osyr-update`), verifies the signed manifest (`osyr.img.xz.manifest` + `.sig`, `ssh-keygen -Y` in the `osyr-image` namespace, same signers as the code) and the sha256 of the xz, writes the root into the free slot (vda2 ↔ vda3) and checks its sha256; then `e2fsck`, new UUID and label, and `resize2fs`. Only later versions (git ancestry in the `update.fetch()` clone).
- **What moves to the new slot** (`migrate`): accounts and passwords (merge of passwd/shadow/group), locale, keyboard, hostname, machine-id, time zone, crypttab, install.conf, the machine's SSH keys, wifi (iwd), Bluetooth, systemd time and brightness, linger; `/etc/osyr` with a three-way merge (what the person changed stays; if it clashes with the new one, the new one goes to `.osyr-new`); the `/home` line of fstab. Then `update code apply` against the new root (`OSYR_UPDATE_ROOT`) so that it ends up on the announced commit.
- **Boot**: `grub.cfg` with `grubenv` (`slot`, `try`). The new slot boots once on trial (`try`, GRUB clears it with `save_env`); if it does not reach `multi-user` (`osyr-boot-ok.service` confirms it) or enters emergency mode (`osyr-fallback.conf`), the next boot goes back to the previous one. "OSYR (previous version)" entry in the menu; `panic=10` so that a broken kernel reboots by itself.
- Chat: `/update` uses `osyr update apply` (image if there is a new version and the system is installed; otherwise, code) and `/update undo` (code first, then the image). The daily notice checks the image first.
- Publishing: `scripts/image-manifest.py`, and `publish.sh img` publishes the manifest next to the image (also `publish.sh manifest`). Defconfig: `resize2fs`.
- **From an installed v0.26**: `/update` (code v0.27.0, brings the new updater) → reboot → `/update` again (v0.27 image in slot B, with the state). v0.26 already has `xzcat`, `ssh-keygen`, `tune2fs`, `e2fsck` and GRUB's `loadenv`; it does not have `resize2fs` (the new root fits as is; it grows in the next image).

## Shell tool and permissions (13 Nov, in v0.32.0)

A call that comes back with the same result as before in the same turn is not answered again: the model is told to stop repeating, and the second time the turn ends with a notice. ## Containers for installing software (13 Nov, in v0.32.0)

Decisions in the table of [TRAINING-PLAN.md](TRAINING-PLAN.md): software is installed in a container (`osyr box`), one default box per user with Debian stable, empty at first, which sees that user's home folder. The official extensions (`osyr ext`) are set aside.

- **Engine in the image:** `podman` without root, with `crun` and `pasta` for the network (Buildroot packages; the kernel needed nothing new). It brings the `shadow` package: `login`, `passwd`, `chpasswd` and `useradd` are now shadow's (`su` is still BusyBox's); `newuidmap` and `newgidmap` are setuid. The range of the `osyr` user is in `/etc/subuid` and `/etc/subgid`.
- **Tried by hand in QEMU** (incremental build, 13 Nov): login on the serial console and `sudo` work with shadow; `podman info` says rootless, overlay, cgroups v2 with systemd; `podman run debian:stable-slim` pulls the image (81 MB), runs Debian 13.7 and `apt-get update` downloads its lists through `pasta`. Two minutes without KVM.
- **Seen there:** booted from the USB image, `/home` is the root partition, with under 1 GB free: little room for programs until the system is installed to a disk.
- **`osyr box`** (`osyr/box.py`): `install` (creates the box the first time: downloads `debian:stable`, sets up the user's language), `remove`, `search`, `list`, `status`, `run <command>` (programs without a window), `update`, `reset` (asks with a token). The box is a container named `osyr-box` run with `--userns=keep-id`: inside, the user is the same user and sees their home folder, the session folder (screen, sound) and `/dev/dri`. Empty folders cover `.ssh`, `.gnupg`, `.config/osyr`, `.local/share/osyr`, `.local/state/osyr`, the keyrings and the box's own storage. What the user asked to install is kept in `~/.local/share/osyr/box/`.
- **`osyr app`** (`osyr/app.py`): `list`, `run <name> [file]`, `stop <name> [--force]`, for the system's applications (never the terminal) and the box's. An application opens on the first free workspace from the third on (the second is the browser's) and the screen goes there. Windows and processes of the box are told apart from the system's by process, so closing the box's terminal does not close the assistant's.
- In the chat: reading commands (`box status/list/search`, `app list`) do not ask; the rest do. Box commands may take up to an hour and show their progress. The fixed prompt gained two lines and lost about as much from the voice and installer lines (not measured on the server yet).
- Tests: `tests/box_cases.py` with a stand-in for podman (34 cases); with the real engine inside the image, in `tests/vm-checks.sh` (they need the Internet).
- **First run in the image (13 Nov, image `d25097b`, vm 153/167):** 13 of the 14 failures were the box's, with one cause: `crun: write: No space left on device` when starting the container. crun copies into a tmpfs what was under it (`tmpcopyup`, the default), so the 64k folders that cover `.ssh`, podman's storage and the rest received the very content they hide. Fixed with `notmpcopyup` (`67d1148`). The other failure, `update-no-reboot`, came from testing an image older than the repository (a later commit touched the library, so the test update restarted `osyr-diskwatch`): not a fault in the code.
- **v0.32.0 published (13 Nov)** on `9ebee2b`: img, signed manifest, update image and ova; boots in QEMU in BIOS and UEFI. Decided by the user: published without repeating the checks in the VM; they test it themselves. **So the box has not yet worked with the real engine in any test**: `box-*` and `app-*` in `vm-checks.sh` are pending, and so is the user's result.
- Known limits: programs that only speak X11 have no screen (no Xwayland in the image): `osyr app run` recognises their error and answers `APP_NEEDS_X11`, with a hint for the assistant to say so and offer another program; an application started by a script under another process name is found by its window's name only; USB disks mounted after the box started are not seen in it.

## Lessons from this milestone

- Changing `configs/osyr_x86_64_defconfig` was not enough: `make` did not reapply it and the new package (sherpa-onnx) did not reach the image. Fixed in the `Makefile`; even so, after touching the defconfig, check `.config`.

- Enabling a package that gives new options to others already built (ICU → HarfBuzz) does not rebuild them: WPE failed to configure without `libharfbuzz-icu` (31 Oct). After enabling large packages, look at which already built packages have `ifeq ($(BR2_PACKAGE_X),y)` for the new ones and run `<package>-dirclean` on those that need it.

- Kconfig silently drops options whose dependencies are missing (it happened with `MESA3D_GALLIUM_DRIVER_IRIS` without LLVM). After touching the defconfig, check that every `BR2_...=y` is still in `build/output/.config`.
- With `BR2_PER_PACKAGE_DIRECTORIES`, changing the configuration of a base package (systemd, PAM) requires a build from scratch (`make clean all`); with ccache it is ~30 min.
- In Buildroot 2026.08's `users.txt`, uid `-1` = system and `-2` = normal user. Better to pin it.
- **wlroots does accept llvmpipe** in virtual machines: with `virtio_gpu` without virgl, mesa falls back to `kms_swrast` on the hardware device, wlroots does not detect it as software and sway draws with 4 llvmpipe threads. That is why mesa is asked for the driver before starting sway, instead of trusting wlroots. Check the real renderer through the threads (`/proc/$(pgrep -x sway)/task/*/comm`).
- The image userland is partly BusyBox (`tar` without `-z`): a script that works on the VPS can fail on OSYR. Test it inside the image (QEMU serial console on a socket).
- QEMU on the VPS runs without KVM: the model speed there (~0.4 tok/s) says nothing; measure on real hardware.
- The disk filled up mid-build (3 Nov: kernel with debug info, 25 GB, plus the old tree). Now `make` runs `scripts/disk-guard.sh` first: it deletes build dirs of packages no longer in the configuration or with an old version (Buildroot never does), images and .ova of versions that are neither published nor current, all but the latest `build/prev-*` and the 3 latest `build/web-prev-*`, and stops if less than 30 GB are free (100 GB without `build/output`; `OSYR_MIN_FREE_GB`). `make prune` only frees. A full `build/output` is ~80 GB.

## Lessons learned (do not repeat)

- No initramfs: disk and USB controllers must be `=y` in the kernel or the root does not appear (black screen).
- GRUB on UEFI reads `/EFI/BOOT/grub.cfg`: Buildroot's points to the FAT partition and gives a black screen.
- Scripts edited on Windows: normalise CRLF and run `chmod +x` **afterwards**.
- Buildroot's generic `grub.cfg` in the root confuses GRUB's search: it is deleted.

## The model on a graphics card: `osyr ai gpu` (14 Nov) — for the next image

- **Build:** `BR2_PACKAGE_LLAMA_CPP_VULKAN` gives one more backend library (`libggml-vulkan.so`) next to the CPU ones, and Mesa gets its Vulkan drivers for AMD (radv) and Intel (anv). llama.cpp compiles its shaders with `glslc`, which Buildroot does not package: `package/shaderc` builds it for the host, with glslang, SPIRV-Tools and SPIRV-Headers at the revisions its `DEPS` names (`external.mk` adds the dependency). **NVIDIA cards are out:** there is no Vulkan driver for them here; the menu says so when it finds one.

## Simulated hardware and the disposable session (23 Nov)

Two pieces of the plan built ahead of their stage because the web sandbox (`ccmai.org/osyr/try/`, decided on 23 Nov) needs both: the hardware doubles of stage 0 and the disposable container of stage 3. The benchmark will use the same two.

The pretend machine is one JSON file (`OSYR_DOUBLES_STATE`), created from a scenario (`tests/doubles/laptop.json`: five wifi networks with passwords, a wired card with no cable, four Bluetooth devices of which one refuses to pair, two displays, a sound card, and a `/sys` with backlight, battery and temperature). - **Session** (`sandbox/session DIR [command]`): the image root (`build/output/target`, read-only, with this repository's `osyr` code over it) as a `bwrap` container: no network, its own process list, the pretend `/sys`, a 256 MB home folder in memory with sample documents (`sandbox/skel`), and no way to become root. Memory (1 GB), processes (256), CPU (two cores) and time (15 min) are capped with `systemd-run --user` and `timeout`. Without a command it starts `osyr-chat`. Everything is gone when it ends.
- **Model gate** (`sandbox/modelgate.py`): the session's only way out is one Unix socket; `sandbox/relay.py` gives the chat a local port for it. The gate answers only `GET /v1/models` and `POST /v1/chat/completions`, rebuilds each request from the fields the chat uses (text messages, tools, `max_tokens` capped), puts the model name and the key in itself, caps requests per session and lets one request at a time through to the server. The server's address and key never enter the container, and its error texts are not passed on.
- **Tried:** `tests/sandbox_cases.py` (native phase, 32 checks): the `osyr` commands against the doubles inside a session, isolation (no network, read-only system, no `sudo`, the upload token hidden, home capped, a new session starts clean) and the gate against the fake provider. By hand: the memory, process and CPU caps, and a whole conversation of `osyr-chat` inside a session through the gate, with the image's `llama-server` and the 4B on the VPS (wifi scan, a volume change with its question).
- **Known limits:** the system files look owned by `osyr` inside (the root folder belongs to the build user; the write protection is the read-only mount). `/proc` shows the VPS's processor count, memory and mount paths. The chat treats the gate as a remote provider, so what `remember` saves is not sent back to the model. `look`, voice, graphical programs, `osyr box` and `sudo` do not work inside. The session runs as the build user: before it is opened to anyone it has to run as a user of its own.
- **Service** (`sandbox/server.py CONFIG`, standard library only): listens on 127.0.0.1 for the web server in front and carries a terminal over a WebSocket (text frames are JSON, binary frames are screen output). Per visitor: access code while the sandbox is private, only the sandbox's own page as origin, one session per address and a number per hour, a queue with the position told as it moves, then the session on a pseudo-terminal with its own gate. It ends the session on time (15 min), after 5 min with nobody typing, when the page closes or when the switch file appears, and deletes its folder. The log has one line per session (length, why it ended, requests and tokens); no conversation is written down. The settings and their defaults are at the top of the file; the work folder needs a short path (a socket lives in it).
- **Page** (`web/try/`): the notice of what the sandbox is and is not, the access code when one is set, and the terminal (xterm.js 5.5.0 and its fit add-on, MIT, copied into `web/try/vendor`) with the site's look and the time left.

- **Tried (23 Nov):** `tests/sandbox_cases.py` now has 45 checks; the service ones run a session whose chat reaches the fake provider, the queue, the limit per address, the switch and the clean-up. By hand, in a headless Chromium on the VPS against the service with the image's `llama-server` and the 4B: the page, a session, a question answered with `osyr net wifi scan`, `/exit`.
- **Installed as a private test (23 Nov, night):** `scripts/publish.sh sandbox` (`sandbox/install.sh`) puts the image root (without the models, with the repository's `osyr` code over it) and the sandbox code in `/opt/osyr-sandbox`, owned by root; the settings in `/etc/osyr-sandbox/config.json` (created once, with a random access code); a systemd unit; a sudo rule; and the page in `ccmai.org/osyr/try/`. Two users that cannot log in: `osyr-try` runs the service and holds the model server's key, `osyr-sandbox` runs the sessions and can read neither the key nor any home folder. The site's settings got two `ProxyPass` lines (WebSocket and status); the page is linked from nowhere.
- **The session, hardened for it:** it takes its settings as options (the service starts it through sudo, which drops the environment), writes nothing outside itself (`/sys` in memory, the two user files through descriptors), is always uid 1000 inside, cannot make user namespaces, and runs under a system-call filter written by `sandbox/seccomp.py`: no new namespaces, mounts, tracing, kernel keys, BPF, performance counters or io_uring, and only Unix and Internet sockets. `sudo` inside answers with a plain sentence.

The gate reaches it on the loopback address under its own TLS name. ## Administration tasks without a real system: a prototype (24 Nov)

The gap [TRAINING-READINESS.md](TRAINING-READINESS.md) names: the plan's goal is an administrator, and nothing simulated services, logs, disks or `sudo`.

- **A whole system to change:** `sandbox/session --system` mounts the image's root with an overlay in memory, so every file can be written and all of it goes with the session. Nothing outside is touched.
- **`tests/doubles/admin.py`** stands in for `systemctl`, `journalctl`, `df`, `du` and `sudo`, from the scenario's `system` table: services with a state, a log and the conditions under which they start (a file that contains or lacks a text, another service, free space); disks whose use follows the files under a folder (the big files of a task are holes, their size counts); a password for `sudo`, remembered five minutes. Changing a service needs `sudo`; `/etc` is closed to writing and `sudo` opens it while its command runs.
- **Two example families** use it (`bench/examples`): a service that does not start because of a misspelt word in its configuration file (four services), and a full disk whose biggest file has to be found and deleted. With the untrained 4B: 3 and 6 of 10, against 90 % on the level 1 examples.
- **Limits:** outside `/etc` the system's files can be written without `sudo`; users, mounts, timers and packages have no double yet. Whether the benchmark's administration tasks are built this way, or on the real image in a virtual machine, is to be decided with the task format.
- **Processes and the clock (24 Nov, later):** reading the models' failures showed two tells of the pretend system that sent them the wrong way: `ps` listed only the session's own shell, and `timedatectl` answered that the system had not been booted with systemd. The same doubles now stand in for `ps`, `pgrep`, `pidof`, `top`, `uptime`, `kill`, `pkill`, `killall` and `timedatectl`. The list of processes is made up on every call: the ones every OSYR laptop has (systemd, the desktop, the chat), one per active service, and the scenario's own (`system.processes`, with the share of the processor each uses). Ending a service's process stops the service, or it comes back if the scenario says it restarts; ending someone else's needs `sudo`; a number that is not pretend is a real job of the shell and gets the real signal. The shells of these sessions leave `kill` to the double (`BASH_ENV`). The clock has a time zone (`set-timezone` moves `/etc/localtime`, so `date` agrees) and is in step when its service is active. A service's program can be a double too (`admin.py daemon NAME -t`), so that `nginx -t` or `sshd -t` check the configuration as the real ones would.
- A third example family uses them: a program that has been hogging the processor, to be found and ended while another program and the model's own server go on (`runaway-process`). The verifier gained `process NAME running|gone` and `timezone ZONE`.
- Tests: `admin-*` in `tests/sandbox_cases.py`.
